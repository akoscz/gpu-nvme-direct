gpu-nvme-direct: GPU-Initiated NVMe I/O on Consumer Hardware

Samuel Cortes · February 2026
Code: github.com/xaskasdf/gpu-nvme-direct · naranjositos.tech

Abstract

We present gpu-nvme-direct, a system that enables a consumer GPU (NVIDIA GeForce RTX 3090) to autonomously initiate NVMe storage I/O operations via PCIe MMIO, entirely without CPU involvement in the data path. Unlike prior work that requires enterprise GPUs with native peer-to-peer (P2P) DMA support, gpu-nvme-direct operates on commodity hardware (AMD Ryzen 5800X, B450 motherboard) costing approximately $2,000, using a tiered approach that degrades gracefully based on available P2P capabilities.

The system works by having a single CUDA thread construct NVMe submission queue entries in host pinned memory, write doorbell registers on the NVMe controller's BAR0 via PTX st.relaxed.mmio.sys instructions, and poll completion queue entries — all without CPU intervention. This is possible because PCIe posted Memory Write TLPs succeed through the AMD data fabric even on consumer platforms where non-posted reads fail.

Evaluated on two NVMe devices: a WD SN530 (PCIe 3.0 x4, 2,666 MB/s, 78% link utilization) and a WD SN740 (3,350 MB/s, 99% link utilization). Compared to CPU-mediated baselines using a faster Samsung 980 PRO (PCIe 4.0 x4), gpu-nvme-direct delivers up to 2.2x higher throughput. Integrated into a streaming inference engine, it achieves 0.06 tok/s for Llama 70B from NVMe alone, and 0.50 tok/s with tiered caching optimizations.

1. Introduction

The explosive growth of large language models (LLMs) has created a fundamental tension between model size and available GPU memory. Models such as Llama 2 70B require ~70 GB in FP16, or ~42 GB in Q6_K quantization — far exceeding the 24 GB VRAM of consumer GPUs like the NVIDIA RTX 3090. Running these models on consumer hardware requires offloading: streaming model weights from slower storage tiers (CPU RAM, NVMe SSD) to the GPU during inference.

Current offloading frameworks (llama.cpp, FlexGen, PowerInfer, PIPO) all route storage I/O through the CPU: the CPU reads data from the NVMe drive into system memory, then copies it to GPU memory via PCIe. This architecture has two fundamental limitations:

  1. The CPU becomes a bottleneck in the data path, serializing I/O operations that could otherwise be pipelined.
  2. CPU cores used for I/O are unavailable for other tasks (preprocessing, scheduling, serving multiple requests).

We ask: can the GPU itself directly initiate NVMe I/O on consumer hardware?

Prior work (BaM, GIDS) has demonstrated GPU-initiated storage access, but exclusively on enterprise hardware (NVIDIA A100, GPUDirect RDMA, PCIe expansion chassis) costing $10,000+. No prior system has achieved GPU-initiated NVMe I/O on commodity consumer hardware.

Our contributions:

  1. First demonstration of GPU-initiated NVMe I/O on consumer hardware (RTX 3090, AMD B450).
  2. Characterization of the PCIe posted-write asymmetry on AMD consumer platforms.
  3. A tiered P2P architecture that degrades gracefully from native P2P (enterprise) to write-only P2P (consumer).
  4. Comprehensive evaluation showing 2.2x throughput advantage over CPU-mediated methods.

2. Background and Motivation

2.1 NVMe Protocol Essentials

NVMe is a register-level interface for accessing storage over PCIe. The host communicates with the NVMe controller through submission queues (SQ) and completion queues (CQ) residing in host memory. To issue a command, the host writes a 64-byte submission queue entry (SQE), then rings the SQ doorbell by writing to a register in the controller's BAR0 MMIO space. The controller fetches the SQE via DMA, executes the command, DMAs data to/from the host buffer, and writes a completion queue entry (CQE) to host memory.

2.2 PCIe Peer-to-Peer on Consumer Platforms

PCIe P2P allows one device to directly access another device's memory or registers without CPU involvement. On enterprise platforms (AMD EPYC, Intel Xeon with PLX switches), P2P is well-supported. On AMD consumer platforms (B450, B550, X570), P2P behavior is asymmetric:

  • Posted writes (Memory Write TLPs): GPU → NVMe BAR0 succeeds. The AMD data fabric routes these correctly.
  • Non-posted reads (Memory Read TLPs): GPU → NVMe BAR0 fails. The root complex drops these, returning 0xFFFFFFFF.

This asymmetry is the key insight enabling gpu-nvme-direct: NVMe doorbells are write-only registers, so posted writes are sufficient to drive the controller.

2.3 GPU MMIO and PTX Instructions

NVIDIA GPUs can access host-mapped memory regions via PTX instructions. For MMIO (memory-mapped I/O), the critical instructions are:

  • st.relaxed.mmio.sys — Store to MMIO space with system scope, generating a PCIe posted write.
  • ld.relaxed.mmio.sys — Load from MMIO space with system scope, generating a PCIe non-posted read (fails on consumer AMD P2P).

2.4 Motivation: LLM Inference from Storage

For Llama 2 70B in Q6_K quantization (~42 GB, 80 layers, ~669 MB/layer), each token generation requires reading the entire model if it doesn't fit in GPU VRAM. At current NVMe speeds (2–7 GB/s), this takes 6–21 seconds per token. Removing the CPU from the data path reduces this time by pipelining I/O operations with higher queue depth utilization.

3. System Design

3.1 Overview

The system consists of a setup phase (CPU-driven) and a data phase (GPU-driven). During setup, the CPU initializes the NVMe controller, creates I/O queues in host pinned memory, builds PRP lists, and passes all state to the GPU kernel. During the data phase, the GPU thread autonomously manages all I/O.

3.2 Tiered P2P Approach

  • Tier 1 (Write-Only P2P): SQ, CQ, and data buffers in host pinned memory. GPU writes doorbells to NVMe BAR0. Works on AMD consumer. No custom kernel module.
  • Tier 2 (Patched P2P): Data buffers in GPU VRAM. NVMe DMA directly to GPU. Requires tinygrad P2P patches.
  • Tier 3 (Native P2P): Everything in GPU HBM. The BaM approach. Requires enterprise GPUs.

3.3 Memory Ordering

Correct operation requires __threadfence_system() between SQ entry writes and doorbell writes, ensuring the NVMe controller sees consistent command data when it fetches the SQE via DMA.

3.4 Pipelined I/O

A single GPU thread maintains up to 32 NVMe commands in flight simultaneously. New commands are submitted before completions for previous ones arrive, keeping the NVMe device's internal parallelism (flash die interleaving) fully utilized.

3.5 Queue Depth Analysis via Little's Law

To saturate a device with bandwidth B and per-command service time ts, the required queue depth is N = B · ts / s. For the SN530 at 256 KB blocks: N ≈ 1.0. At 4 KB blocks: N ≈ 9.0. QD=32 provides ample headroom for all block sizes. CPU methods show no queue depth scaling because the kernel I/O stack serializes requests — the effective QD at the device is always ~1.

4. Implementation

gpu-nvme-direct is implemented in ~4,500 lines of C and CUDA code. Key components:

  • mmio_ops.cuh: PTX inline assembly for mmio_write32, mmio_read32, and 64-bit variants.
  • sq_submit.cuh: Constructs 64-byte NVMe Read/Write SQEs with aligned 32-bit stores.
  • cq_poll.cuh: Phase-bit-based completion detection from host pinned memory.
  • controller.c: Full NVMe controller initialization per NVMe spec 2.0.
  • dma_alloc.c: Virtual-to-physical translation via /proc/self/pagemap for PRP lists.

NVIDIA Driver Patch: On Linux 6.17, cudaHostRegisterIoMemory fails because follow_pfn() was removed in kernel 6.12. We patched the NVIDIA open-source kernel module to compute the PFN from the VMA's vm_pgoff for VM_PFNMAP mappings.

VFIO Setup: The test NVMe (SN530) is passed through to userspace via VFIO in no-IOMMU mode. After VFIO binding, we restore D0 power state and re-enable Memory Space + Bus Master via setpci.

5. Evaluation

5.1 Throughput at QD=32

gpu-nvme-direct uses the slower SN530 (Gen3, ~3,400 MB/s max); CPU baselines use the faster 980 PRO (Gen4, ~7,000 MB/s max). Despite this 2x asymmetry favoring baselines:

Normalized: gpu_direct achieves 78.4% of Gen3 link; cpu_memcpy achieves only 24.7% of Gen4 link. The GPU path extracts 3.2x more available bandwidth.

5.2 Queue Depth Scaling

gpu-nvme-direct shows 1.4–2.3x throughput improvement from QD=1 to QD=32. CPU methods show no meaningful scaling (1.0x) because the kernel serializes I/O.

5.3 Latency

At 4 KB/QD=32, the inter-completion latency is only 1.5 μs (std dev: 0.23 μs). At QD=1, gpu-nvme-direct achieves 10.6 μs vs 19.6 μs for cpu_memcpy — a 46% reduction by bypassing the kernel I/O stack.

5.4 CPU Utilization

gpu-nvme-direct: 8.5% average (CUDA runtime overhead only). The CPU is entirely free for other tasks during GPU-driven I/O.

5.5 cuFile on Consumer Hardware

NVIDIA cuFile (GPUDirect Storage) performs identically to cpu_pinned on GeForce RTX 3090, confirming GDS falls back to a CPU-mediated path on consumer GPUs. gpu-nvme-direct fills this gap.

7. Related Work

GPU-Initiated Storage Access

BaM (ASPLOS '23) demonstrates GPU-orchestrated on-demand storage via GPUDirect RDMA on A100 GPUs, achieving 45.8M IOPs across 10 SSDs. GIDS (VLDB '24) extends BaM to GNN training, reaching 582x speedup over DGL. Both require enterprise hardware ($10k+). gpu-nvme-direct works on consumer hardware (~$2k) using only PCIe posted writes.

LLM Inference on Constrained Hardware

FlexGen (ICML '23) offloads across GPU/CPU/disk via linear programming. PowerInfer (SOSP '24) exploits activation sparsity. PIPO designs fine-grained offloading for consumer devices. HeadInfer offloads KV cache at per-head granularity. ServerlessLLM (OSDI '24) optimizes checkpoint loading to 12 GB/s from RAID0-NVMe. None achieve GPU-initiated storage access — all route I/O through the CPU.

8. Discussion and Future Work

Tier 1 Bandwidth Ceiling

The GPU's PCIe 3.0 x8 link (B450 lane sharing) provides ~6.5 GB/s to host memory — roughly 2x the SN530's 3.4 GB/s. The NVMe is still the bottleneck, not the extra hop, but the margin is tight. A Gen4 x4 NVMe at full speed (7 GB/s) would exceed the GPU link, motivating Tier 2 (direct NVMe DMA to GPU VRAM).

Why a Single Thread Suffices

The I/O management thread spends ~2 μs per command, far below the NVMe service time. It consumes one warp slot, leaving 81 SMs free for tensor computation.

Bandwidth Utilization: 78% vs BaM's 90%

The 12-point gap is attributable to Tier 1's extra host memory hop (2 PCIe traversals vs 1). Despite this, gpu-nvme-direct extracts 3.2x more bandwidth than CPU-mediated methods on the same platform.

Synergy with Quantization

NanoQuant (sub-1-bit) compresses Llama 2 70B from 42 GB to ~8 GB. Combined with gpu-nvme-direct at Gen4 bandwidth: projected ~0.5 tok/s. Quantization reduces I/O volume; GPU-initiated I/O reduces transfer latency.

Limitations

  1. Device asymmetry in evaluation (SN530 Gen3 vs 980 PRO Gen4).
  2. Write support implemented but not benchmarked.
  3. Sequential access only; random I/O unevaluated.
  4. NVIDIA driver patch ties to specific kernel/driver versions.

9. Conclusion

We presented gpu-nvme-direct, the first system (to our knowledge) that demonstrates GPU-initiated NVMe I/O on consumer hardware. Using a GeForce RTX 3090 on an AMD B450 platform, a single CUDA thread autonomously manages NVMe I/O queues without any CPU involvement in the data path.

Our key insight is that PCIe posted writes succeed on AMD consumer platforms even where P2P reads fail. gpu-nvme-direct achieves 2,666 MB/s (78% of link bandwidth), outperforming CPU-mediated methods by up to 2.2x despite using a slower NVMe device.

This work opens the door to GPU-centric storage access on commodity hardware, with applications in LLM inference, graph analytics, and any workload where GPU memory is insufficient to hold the full working set.
